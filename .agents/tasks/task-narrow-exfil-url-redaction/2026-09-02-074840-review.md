# Narrow the frontend exfil-URL redaction to a code-owned exact-host allowlist

`sanitizeExfiltrationUrls` in `website/src/utils/sanitize.ts` was rewritten to stop redacting legitimate long, query-heavy links (issue #7820: GitHub prefilled-issue URLs and `monitorportal.amazon.com` dashboards). The checks are now split to mirror the *shape* of the backend classifier `_exfil_url_warning`: an unconditional tier (heavy percent-encoding `EXFIL_PERCENT_RE` + hard credential markers `EXFIL_CREDENTIAL_RE`) that runs for every host, and a heuristic tier (base64 blob `EXFIL_B64_RE` + aggregate query length ≥ 200) that is skipped only for a tiny code-owned exact-host allowlist `EXFIL_EXEMPT_HOSTS = {github.com, monitorportal.amazon.com}`, matched lowercased and exactly (never by suffix). The frontend cannot reach the backend's companion-supplied exempt-host set at render time, so the list is hard-coded rather than wired through; JWT credential-pattern parity and the Safari-14 no-lookbehind constraint are left intact.

Watch for: (1) **confirmed** — for the two exempt hosts the base64-blob and length heuristics no longer run, so a sub-200-char query at `github.com`/`monitorportal.amazon.com` carrying a base64 conversation blob renders unredacted; the unconditional tier does not catch base64. This is the deliberate tradeoff, but it is the exact exfil shape the heuristic was built for and should be acknowledged as accepted residual. (2) **possible** — the exempt match is port-agnostic, so `https://github.com:443/...` is also exempt; whether that matches or diverges from backend posture is worth a glance.

**Verdict**: APPROVED

## High-level view

The narrowing is coherent with the backend's layering: the unconditional tier (percent-encoding + AWS/SSH/PEM/Slack markers) runs for every host including the two exempt ones, and only the softer base64/length heuristics are lifted for the allowlist. The exact, lowercased, no-suffix match is directly tested against a `github.com.evil.example` look-alike and a mixed-case `GitHub.com`.

The residual risk is real and inherent to the policy, not a bug: at an exempt host, a base64-encoded blob shorter than 200 chars with no long consecutive percent run rides free. `github.com` is a plausible sink (an attacker-owned repo's `issues/new?body=<blob>`), so this is not a purely academic gap. It is defensible because the guard is display-only (the agent can already fetch any URL via tools, per the issue) and because a hard-coded two-host list is far narrower than exempting all well-formed https URLs — but it is worth stating explicitly in the residual-risk note rather than leaving implied.

The frontend/backend divergence is intentional and now documented, but the frontend runs its tiers on the raw query only (no percent-decode loop, no `_contains_fixed_credential`). Those gaps predate this change and are out of scope, yet they mean the doc's "unconditional tier catches an AWS key on an exempt host" claim holds only for the literal `AKIA…` form, not a percent-encoded one.

The `URL_RE` parsing quirks (no userinfo handling, port-agnostic host capture) are pre-existing and unchanged by this diff. They interact with the new exempt match but do not make anything worse than the baseline.

### Exempt-host tier lift and the base64 residual

For a non-exempt host the behavior is unchanged from baseline (length ≥ 200 or a 40-char base64 run redacts); for `github.com` and `monitorportal.amazon.com` both of those checks are skipped and only `EXFIL_PERCENT_RE` (20+ consecutive `%XX`) and `EXFIL_CREDENTIAL_RE` (literal `AKIA/ASIA`, `ssh-rsa/ssh-ed25519`, `BEGIN…PRIVATE KEY`, `xox[bpas]-…`) remain. A base64 conversation blob under 200 chars carries no percent-octets and matches no literal credential marker, so at an exempt host it is not redacted:

```
https://github.com/attacker/repo/issues/new?body=<~150 chars base64 of conversation>
  → host github.com is exempt → base64/length heuristics skipped
  → no 20+ consecutive %XX, no AKIA/ssh/BEGIN/xox literal
  → renders unredacted
```

This is the precise shape the heuristic was built to stop, and `github.com` is a usable sink via an attacker-owned repo's prefilled-issue form. The justification — display-time guard, not a fetch restriction; a two-host code-owned list is the minimal narrowing that fixes the false positives without deleting the guard for arbitrary hosts — is sound, but it belongs in the residual-risk note explicitly. The frontend is not weaker than the backend's host-exemption tier here; the backend has the same structural property for its exempt hosts.

### Port-agnostic exempt match

The port is captured in a separate group and never consulted, so `https://github.com:443/...` is exempt. The backend's OAuth and Slack carve-outs explicitly refuse when a port is present, but its plain host-exemption tier (`_dom in exempt_hosts`) does not gate on port either, so the frontend matches the backend's *host* tier. This is not a widening — the host still has to be exactly `github.com` — but the choice is undocumented and reads as an omission next to the OAuth/Slack gates that do check port.

### Frontend/backend divergence and doc accuracy

Two mechanical gaps relative to the backend are pre-existing (present in the baseline `EXFIL_PATTERNS`, unchanged here) and out of scope, but they bound what the doc's wording actually promises:

- The frontend scans the **raw query only**; the backend runs a bounded multi-pass `unquote_plus` decode loop and re-scans. A percent-encoded credential evades the frontend.
- The frontend has no equivalent of `_contains_fixed_credential` (GitHub/Stripe/etc. canonical tokens); only the older AWS/SSH/PEM/Slack floor is mirrored.

Concretely, a percent-encoded `AKIAIOSFODNN7EXAMPLE` is 20 octets — below `EXFIL_PERCENT_RE`'s `{20,}` (needs 21) and not matched by the raw credential RE — so it passes the frontend on every host while the backend catches it after decoding. The doc bullet says the unconditional tier still flags "an AWS key … on an exempted host"; that holds for the literal form the tests exercise, so the wording is fine as long as it is read as the literal marker, not the encoded one.

### Test coverage

The 11 tests cover the narrowing: long benign queries at both exempt hosts render unchanged; arbitrary hosts still redact on length and on a 40-char base64 run; the suffix look-alike and mixed-case host are both pinned; and each unconditional marker (AWS id, ssh/PEM, Slack token, 21-octet percent run) still redacts at an exempt host, with a sub-threshold percent run left alone.

Not tested: the accepted-residual path itself — a short base64 blob (< 200 chars, no percent run) at `github.com` rendering through. Adding that assertion would pin the tradeoff as intentional and would fail loudly if someone later re-tightened the exempt tier, a direction the falsification check (revert → 3 exempt tests fail) does not cover.
